
================================================================================
        DATABASE INDEXING ALGORITHM  —  PERFORMANCE BENCHMARK REPORT
        Linear Scan  vs  Hash Index (unordered_map)  vs  B-Tree Index
================================================================================

ALGORITHMS
----------
  Linear Scan   No SQLite index on 'name'.  Every name-based lookup
                performs a full sequential table scan.  Complexity: O(n).

  Hash Index    No SQLite index.  An in-memory std::unordered_map<name,rowid>
                is maintained by the application.  Lookup is O(1) average;
                inserts and deletes also update the map.

  B-Tree Index  Native SQLite CREATE INDEX on the 'name' column.
                SQLite automatically uses the B-Tree for WHERE name=? queries.
                Complexity: O(log n) lookup, O(log n) insert overhead.

METHODOLOGY
-----------
  * Each algorithm operates on its own isolated table.
  * Database opened with WAL journal mode, NORMAL sync, 16 MB page cache.
  * Inserts wrapped in explicit BEGIN/COMMIT transactions.
  * Updates and deletes also transacted to isolate their cost.
  * Lookup  : 100 point-lookups by name (random, seed=42).
  * Range Query : name BETWEEN low AND high (matches 100 records).
  * Prefix Search : name GLOB 'Employee_0001*' (matches ~1000 records at large scales).
  * Ordered Scan : SELECT all non-deleted records ORDER BY name.
  * Update  : 100 records updated by primary-key id.
  * Delete  : 50 unique soft-deletes (deleted=1).
  * Range Scan: SELECT all non-deleted records in id order.
  * Compact : VACUUM the entire database.
  * (*) marks the fastest algorithm for each operation.

================================================================================
 ANALYSIS & RECOMMENDATIONS
================================================================================

 1. INSERT PERFORMANCE
    All strategies issue inserts into SQLite pages inside transactions.
    B-Tree index adds overhead per insert to maintain the sorted index tree.
    Hash strategy maintains the in-memory map (negligible cost vs. disk I/O).
    Expected: Linear (fastest) ~= Hash < B-Tree (index maintenance overhead).

 2. POINT LOOKUP BY NAME
    Hash achieves O(1) average via unordered_map, then O(1) by primary key.
    B-Tree achieves O(log n) via the SQLite native index.
    Linear performs O(n) full table scan — degrades severely with data size.
    Expected: Hash < B-Tree << Linear (gap widens as n increases).

 3. UPDATE PERFORMANCE
    Updates target a known primary key (O(1) SQLite row access).
    B-Tree must update its index entry for the changed 'name' field.
    Hash must update the in-memory map keys on name change.
    Expected: similar for all three; minor overhead in Hash and B-Tree.

 4. B-TREE ADVANTAGE (Range, Prefix, Ordering)
    Range Query: B-Tree uses index to jump to start and scan exactly k rows (O(log n + k)).
    Prefix Search: B-Tree uses index for GLOB matches (O(log n + k)).
    Ordered Scan: B-Tree avoids O(n log n) filesort by traversing index.
    Linear & Hash: Force a full table scan O(n) for all three, plus filesort for ordering.
    Expected: B-Tree Dominates << Hash ~= Linear.

 5. RANGE SCAN (No Order)
    All strategies read the full active record set sequentially — O(n).
    No meaningful difference expected between strategies.

 6. SCALABILITY SUMMARY
    As n grows from 1K to 50K, Linear lookup degrades ~50x.
    Hash lookup stays nearly constant (in-memory O(1)).
    B-Tree lookup grows logarithmically (~log2(50000/1000) = ~5.6x slower).

 RECOMMENDATIONS
    - Read-heavy workloads, large datasets : Use B-Tree indexes (balanced).
    - Lookup-dominant, memory available    : Use Hash index for max speed.
    - Range queries, sorting by column     : Use B-Tree indexes (essential).
    - Write-heavy, no point lookups needed : Linear (no index overhead).
    - Never leave large tables un-indexed  : Linear degrades rapidly.

 NOTE: Timings depend on disk speed, OS, CPU cache, and SQLite page cache.
 For production analysis, run multiple passes and average the results.
 (*) marks the fastest algorithm in each row.
